## Архитектурное решение по трейсингу

### Проблемные места которые нужно покрыть трейсингом

В первую очередь трейсингом нужно покрыть места, в которых может потеряться заказ:

- Shop Api -> Mes Api - order_id, issuer, timestamp
- Mes Api -> Crm Api - order_id, issuer, timestamp
- Shop Api -> Crm Api  - order_id, issuer, timestamp

Так же нужно покрыть взаимодействия с бд, чтобы определить медленные запросы и ошибки:

- Shop Api -> Shop Db - duration
- Crm Api -> Crm Db - duration (после того как появится бд у CRM)
- Mes Api -> 3d file storage - duration

И покрываем трейсингом RabbitMq, данные order_id, producer, consumer, timestamp 

### Мотивация

В систему нужно добавить трейсинг с целью определения причин озникновения списка проблем:
- Потери заказов
- Долгая обработка заказов
- Сокращение времени реагирования и устранения проблем.

Внедрение трейсинга сделает прозрачным путь заказа между система и поможет быстро определить проблемную точку и 
соответственно уменьшить скорость устранения инцидента.

Метрики на которые повлияет внедрение трейсинга:
- MTTD - среднее время обнаружения проблемы
- MTTR - среднее время необходимое для восстановления
- Обнаружение потерь сообщений в RabbtiMq

### Предлагаемое решение
Стек:
- Для отправки трейсов из Java приложений используем библиотеку Micrometer Tracing, а для C# (Mes) будет использоваться OpenTelemetry
- Jaeger для хранения трейсов
- Grafana для визуализации (используем ее, а не стандартный UI Jaeger так как там же будут метрики)

Почему не Tempo

Tempo нам не подходит по двум причинам:
- Tempo использует объектное хранилище (S3) и не имеет полнотекстового индекса по тегам. Поиск трейсов по order_id, 
issuer или timestamp будет выполняться медленно, что критично для оперативного выявления потерянных заказов. Нам нужен быстрый поиск по атрибутам, а Tempo оптимизирован под сценарий "нашел трейс по ID из лога/метрики".

- В будущем мы планируем использовать Elasticsearch как централизованное хранилище для агрегации логов. В этом контексте выбор между Jaeger и Zipkin становится более логичным, так как оба поддерживают Elasticsearch

Между Jaeger и Zipkin выбор пал на Jaeger по следующим причинам:
- Jaeger лучше масштабируется, так как у него модульная архитектура
- Нативная поддержка OTLP, а в силу того что нам предстоит интеграция c С#, это конкурентое преимущество
- У Jaeger лучше поддержка, нет риска остаться без обновлений

### Компромиссы

- Проприетарная система MES требует дорогостоящей доработки, для внедрения трейсинга, поэтому на первом этапе трейсинг будет ограниченным  
- Высоконагруженные API могут использовать только ограниченный/выборочный трейсинг, чтобы сильно не аффектить производительность системы.
- Для хранения трейсов требуется значительный объем памяти

### Безопасность

Grafana и Jaeger будут расположены внутри контура приложения. Если потребуется доступ из вне, то обеспечить его через vpn
и использовать многофакторную аутентификацию. Доступ к системе трейсинга будет только у пользователей с ролями:  "Поддержка",
"Разработчики", "Администраторы"
